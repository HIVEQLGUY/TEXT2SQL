# 表治理优先级判断规则

生成日期：2026-07-09

本文档用于第三阶段：定义表资产治理优先级规则。它只定义 `importance_candidate` 的判断口径，不直接生成质量规则，不直接修改 BI 工具配置，也不作为删除表的依据。

## 1. 基本原则

治理优先级必须基于多类证据综合判断，不能只看表名、数仓层级或单个元数据字段。

优先使用以下证据：

| 证据类型 | 典型来源 | 作用 |
| --- | --- | --- |
| 业务消费证据 | 报表、数据集、AI 调用、外部写出、业务方直接使用记录 | 判断是否直接影响业务使用 |
| 任务链路证据 | 生产任务、消费任务、上下游任务依赖、SQL 引用关系 | 判断是否处于核心链路或关键中间节点 |
| 表血缘证据 | 上游表、下游表、下游表数量、结果表链路 | 判断影响范围 |
| 字段语义证据 | 成本价、推广费、销售额、订单、库存、利润、商品、店铺等字段 | 判断业务核心程度 |
| 物理状态证据 | 行数、分区、最新分区、更新时间、未使用天数、空表状态 | 判断是否活跃、废弃或异常 |
| 元数据完整性证据 | owner、业务日期、主键、分区键、表注释、字段注释 | 判断是否可治理、是否需要人工复核 |

弱证据只能辅助判断：

- `warehouse_layer_raw` 只能作为线索，不能单独决定优先级。
- 表名规则只能作为弱证据，不能单独决定优先级。
- 命名像临时表、备份表、持久化表的资产，如果有真实报表、数据集、任务或外部使用，不能自动降级。
- ODS/DWD/DWS/ADS 等层级信息必须结合字段、血缘、使用情况和物理状态一起判断。
- 有下游依赖但长期未更新，不自动视为异常或 P0。配置表、历史快照、周期固化表、一次性口径表可能本来就不需要持续更新；如果没有报表、近期查询、核心金额字段、S/A 结果表影响或外部直接消费证据，默认不生成强质量规则，也不进入人工确认清单。

## 2. 判定顺序

推荐按以下顺序判断：

1. 先识别 `REVIEW`：如果证据冲突、来源不明、关键元数据缺失，优先进入复核。
2. 再识别 `S` 和 `A`：优先保护直接影响业务决策、核心报表、核心数据集、外部系统和关键结果表的资产。
3. 再识别 `B` 和 `C`：根据下游影响、任务链路、活跃度、字段核心程度分层。
4. 最后识别 `IGNORE`：只对长期不用、无下游、无消费、无近期查询、空表或明显废弃临时表给出忽略候选。

`IGNORE` 不是删除指令。所有 `IGNORE` 候选必须保留证据，后续删除、下线、归档必须另走人工确认流程。

## 3. S 级候选

满足以下任一类强证据，可列为 `S` 级候选：

- 被 AI 调用、外部系统、业务方直接使用。
- 被核心报表或核心数据集使用。
- 是利润、成本、订单、库存、销售、推广费等核心经营分析结果表。
- 是多个下游链路共同依赖的关键结果表。
- 一旦异常会直接影响业务决策、经营复盘、对外输出或核心看板。

推荐证据组合：

- 有报表/数据集/AI/外部写出使用证据。
- 有生产任务或多个下游任务消费。
- 字段中包含利润、成本价、推广费、销售额、订单金额、库存数量等核心指标。
- 查询次数高或被近期频繁使用。
- 行数、存储量、分区和更新时间表明该表处于活跃生产状态。

典型处理建议：

- `quality_rule_needed` 通常为 `yes`。
- 后续应优先配置完整性、及时性、行数波动、核心字段非空、金额/成本/推广费合理性、主键唯一性、业务日期连续性等规则。
- 规则上线前应确认 owner 和业务口径。

## 4. A 级候选

满足以下任一类证据，可列为 `A` 级候选：

- 被重要报表、数据集或多个任务使用。
- 是核心链路中的重要中间表。
- 包含成本价、推广费、销售额、库存、订单、退款、利润等核心指标字段。
- 是重要维表，例如商品、店铺、组织、人员、渠道。
- 不是最终业务结果表，但异常会明显影响 S 级或核心 A 级资产。

推荐证据组合：

- 有数据集、任务、SQL 引用或下游表使用。
- 字段中有核心金额、成本、推广、库存、订单、商品、店铺等语义。
- 最近仍在更新或查询。
- 存在上游和下游，且位于主链路中。

典型处理建议：

- `quality_rule_needed` 通常为 `yes` 或 `review`。
- 如果 owner、主键、业务日期明确，应进入规则配置候选。
- 如果是重要中间表但业务口径不清，应先进入 `REVIEW` 或补充元数据。

## 5. B 级候选

满足以下任一类证据，可列为 `B` 级候选：

- 有下游任务使用，但没有直接报表或业务消费。
- 是常规中间层、汇总层、明细层。
- 近期活跃，但影响范围有限。
- 对单条或少量业务链路有影响，但不是核心结果资产。
- 是影响 S/A 结果表的中间过程表，即使命名像临时表，也至少应为 `B` 或 `REVIEW`。

推荐证据组合：

- 有任务依赖或 SQL 引用。
- 有上游或下游，但报表、数据集使用较少。
- 字段中有业务日期、金额、数量、状态、关联键等治理价值字段。
- 最新更新时间较近，或近期有查询。

典型处理建议：

- `quality_rule_needed` 通常为 `review`。
- 可先配置轻量规则，例如行数不为 0、任务成功、业务日期可用、关键关联键非空。
- 若发现其影响 S/A 表，应升级为 `A` 或进入 `REVIEW`。

## 6. C 级候选

满足以下特征，可列为 `C` 级候选：

- 低频使用。
- 单一任务内部使用。
- 影响范围小。
- 无核心金额、成本、库存、推广费、销售额等业务字段。
- 有一定活跃度，但缺少直接业务消费和关键链路证据。

推荐证据组合：

- 下游任务少，报表/数据集使用少或没有。
- 查询次数低。
- 字段偏辅助、状态、配置、日志、过程信息。
- 行数较小或更新频率较低，但未达到废弃标准。
- 有下游任务引用但长期未更新，且没有直接业务消费或核心风险证据时，可视为静态/周期固化候选，不因“下游存在”自动升级。

典型处理建议：

- `quality_rule_needed` 通常为 `review`。
- 暂不作为第一批质量规则配置重点。
- 可先补齐 owner、表注释、主键、业务日期等资产元数据。
- 静态/周期固化候选默认不配置 freshness、行数波动等持续性规则；只有业务方确认它应周期更新时才重新纳入治理。

## 7. IGNORE 候选

满足以下多项证据，可列为 `IGNORE` 候选：

- 长期未使用。
- 无下游、无报表、无数据集、无近期查询。
- 物理数据为空或长期不更新。
- 明显为废弃临时表、备份表、一次性过程表。
- 缺少业务消费证据，且没有链路证据表明它影响 S/A/B 资产。

推荐证据组合：

- `unused_days` 长期偏高。
- `row_count=0` 或长期无最新分区/更新时间。
- `used_by_report_count=0`、`used_by_collection_count=0`、`queried_recently_count=0`。
- `downstream_task_count=0`、`downstream_table_count=0`。
- 无 owner 或 owner 不可信。

约束：

- `IGNORE` 只是治理低优先级候选，不是删除、停用、清表、归档指令。
- 必须保留证据项，说明为什么暂不治理。
- 如果后续发现业务方、报表、外部系统或 S/A 链路依赖，应立即移出 `IGNORE`。

## 8. REVIEW

满足以下任一情况，应列为 `REVIEW`：

- 元数据证据冲突。
- 命名像临时表，但有重要下游、报表、数据集、查询或外部使用。
- 元数据看似不用，但业务名称、字段或链路像核心表。
- 无法识别 owner、业务日期、主键或使用关系。
- 涉及敏感配置、权限、账号、外部写出或来源不明。
- 数仓层级、表名、字段语义和实际使用情况互相矛盾。
- 物理状态显示长期不更新，但仍有近期查询或业务消费。

典型冲突示例：

| 冲突类型 | 处理 |
| --- | --- |
| 临时/持久化命名，但被报表或数据集使用 | 标记 `REVIEW`，不能直接降为 `IGNORE` |
| `unused_days` 很高，但近期有查询、报表或外部直接消费 | 标记 `REVIEW`，核查未使用天数字段口径 |
| `unused_days` 很高且只有下游任务引用，没有报表、查询、核心字段或 S/A 影响 | 视为静态/周期固化候选，默认不生成强规则、不进入人工确认 |
| 表名像核心订单/销售/库存表，但无任何使用证据 | 标记 `REVIEW`，确认是否是隐藏消费或废弃资产 |
| 字段包含成本价/推广费/销售额，但 owner、主键、业务日期缺失 | 标记 `REVIEW`，补齐治理前置元数据 |
| 上游/下游关系断裂，但任务或 SQL 引用仍存在 | 标记 `REVIEW`，核查血缘采集完整性 |

## 9. 优先级升级和降级规则

升级规则：

- 被核心报表、核心数据集、AI 或外部系统使用时，至少为 `A`，核心决策链路可升为 `S`。
- 直接影响 S 级资产的中间表，至少为 `B`；影响多个 S/A 资产时可升为 `A`。
- 命名像临时表但有真实业务消费，不按临时表降级，应进入 `A/B/REVIEW`。
- 包含成本价、推广费、利润、销售额、库存等核心字段，且有使用或链路证据时，至少为 `A/B`。
- 重要商品、店铺、组织、人员、渠道维表，若被核心链路使用，至少为 `A`。

降级规则：

- 无下游、无报表、无数据集、无近期查询，且长期未更新，可降为 `IGNORE`。
- 只有下游任务引用但长期未更新，且无报表/近期查询/核心金额字段/S/A 影响，可降为静态/周期固化观察候选，不生成强规则。
- 只有单一任务内部使用、无核心字段、影响范围小，可降为 `C`。
- 表名看起来重要但没有任何使用、血缘和物理活跃证据，不直接升为 `S/A`，应先 `REVIEW`。
- `warehouse_layer_raw` 显示为 DWS/ADS 但没有消费、查询、链路和核心字段证据时，不单独升优先级。

## 10. 与质量规则配置的关系

本阶段只定义治理优先级，不直接生成质量规则。

后续进入质量规则配置时，可按以下方向使用优先级：

| 优先级 | 后续治理动作 |
| --- | --- |
| S | 第一批配置质量规则，要求 owner、业务日期、主键、核心字段规则齐全 |
| A | 第一批或第二批配置质量规则，优先覆盖核心字段和链路及时性 |
| B | 配置轻量规则或作为 S/A 链路补充规则 |
| C | 暂缓配置复杂规则，优先补资产元数据 |
| IGNORE | 暂不配置规则，只保留证据，禁止直接删除 |
| REVIEW | 先人工复核和补证据，再决定是否进入 S/A/B/C/IGNORE |

## 11. 输出要求

每张表的优先级判断应至少保留以下证据：

- 使用证据：报表、数据集、AI、外部系统、查询、任务消费。
- 血缘证据：上游任务、下游任务、上游表、下游表。
- 字段证据：核心指标字段、日期字段、主键候选、关联键候选。
- 物理证据：行数、数据大小、分区、最新更新时间、未使用天数。
- 元数据证据：owner、表注释、字段注释、原始层级线索。
- 冲突证据：任何导致 `REVIEW` 的不一致点。

如果证据不足，不能强行判定为高优先级；应优先给出 `REVIEW`，并说明缺少哪些证据。
