# 智能问数系统架构草案

## 1. 教程架构的可复用思想

教程第一、第二节提供的核心思想可以复用：

- 不让大模型直接面对全量数据库盲写 SQL。
- 先构建可检索的元数据知识库。
- 用户提问后，先召回相关表、字段、字段值和业务口径。
- 将召回结果整理成结构化上下文。
- 大模型基于上下文生成 SQL。
- SQL 先校验，再执行。
- 整个流程需要可观察、可复盘、可调试。

这些思想适用于本项目，但教程中的表模型、元数据配置方式和具体组件不作为强制实现。

## 2. 目标架构

系统分为五层：

1. 数据源层：抖音主题域数据表及后续其他主题域数据表。
2. 元数据协作层：钉钉 AI 表格，用于生成、补充和治理元数据。
3. 元数据运行层：项目自己的元数据数据库，保存运行时权威元数据。
4. 检索与理解层：根据用户问题召回相关表、字段、字段值、计算公式、依赖关系和注意事项。
5. 问数执行层：生成 SQL、校验 SQL、执行 SQL、返回结果并记录日志。

## 3. 元数据同步链路

目标同步链路：

1. 钉钉 AI 表格维护表元数据和字段元数据。
2. 定时任务调用钉钉开放平台接口拉取元数据。
3. 同步任务做字段校验、格式标准化和变更比对。
4. 将标准化后的元数据写入元数据数据库。
5. 根据元数据构建或更新检索索引。
6. 在线问数流程读取元数据数据库和检索索引。

同步任务需要支持：

- 全量同步
- 增量同步
- 失败重试
- 变更日志
- 字段合法性校验
- 元数据版本记录

## 4. 元数据表设计方向

初步建议将运行时元数据拆为以下核心表，具体字段后续根据钉钉表格和抖音主题域数据确认：

- `meta_table`：表元数据。
- `meta_field`：字段元数据，包含普通字段、度量字段、时间字段、技术字段和带计算公式的业务字段。
- `meta_field_dependency`：字段直接依赖和血缘关系。
- `meta_field_value`：字段示例值、枚举值或高频候选值的结构化缓存。
- `meta_sync_job`：钉钉同步任务记录。
- `meta_sync_change_log`：元数据变更记录。
- `query_run`：问数运行记录。
- `query_step`：问数流程节点记录。

是否单独建立指标表暂不强制。当前方向是先不在产品概念上区分指标和字段，但数据库层可以保留扩展空间，避免未来需要支持复杂指标口径时大改。

## 5. 检索设计方向

教程使用 `MySQL + Qdrant + Elasticsearch + TEI`。本项目不因为本地资源限制而主动降级，但最终组件选择要服务长期可维护性。

初步判断：

- 结构化元数据必须进入关系型数据库。
- 字段名、字段中文名、字段描述、业务含义、使用注意事项适合做语义检索。
- 枚举型或文本型字段值适合做关键词检索或混合检索。
- 字段依赖、计算公式、分区字段、主键等信息必须在 SQL 生成前进入上下文。
- 抖音主题域如果字段多、值多，检索索引要从第一阶段就按可扩展方式设计。
- 同一字段应支持多个语义入口，例如字段名、字段中文名、字段描述、业务含义、别名、适用场景。
- 字段值索引用于解决真实取值问题，例如库中存的是“浙江”还是“浙江省”。
- 不是所有字段都做字段值索引，应优先覆盖文本型、枚举型、经常作为筛选条件的属性字段。

后续在确认服务器和数据库资源后，再决定使用 Qdrant、Elasticsearch、OpenSearch、PostgreSQL pgvector、MySQL 全文索引或其他替代方案。

## 6. 问数智能体流程

建议目标流程：

1. 接收用户问题。
2. 识别主题域、业务对象、时间范围、指标/度量、维度、筛选条件。
3. 并行召回相关表元数据、字段元数据、计算字段/业务口径、字段真实取值和字段依赖。
4. 将召回结果按主题域、库、表、字段组织成层次化上下文。
5. 补齐主键、外键、分区字段、依赖字段和计算公式。
6. 过滤当前问题不需要的表、字段、字段值和业务口径。
7. 补充当前时间、数据库类型、数据库版本、权限边界等额外上下文。
8. 生成 SQL。
9. 做 SQL 安全校验和语法校验。
10. 必要时根据错误信息修正 SQL。
11. 使用只读账号执行 SQL。
12. 返回结果、图表建议和运行过程记录。

建议保留 LangGraph 或同类图工作流框架，用于表达：

- 固定顺序节点。
- 并行召回节点。
- 校验失败后的条件分支。
- 运行过程流式输出。
- 节点级耗时、错误和上下文记录。

如果早期实现阶段暂不接入完整 LangGraph，也必须保持节点化边界，避免把问数流程写成单个长函数。

## 7. 安全与权限

即使项目负责人可以提供数据库超级管理员账号和云服务器超级管理员账号，应用运行时仍应遵守最小权限原则：

- 超级管理员账号只用于环境初始化、建库、授权、排障和迁移。
- 在线问数执行 SQL 默认使用只读账号。
- 模型生成 SQL 只允许 `SELECT` 类查询。
- 禁止多语句执行。
- 禁止访问未授权库表。
- 高风险查询需要记录并进入人工确认或拒绝。

这不是资源限制，而是工程安全边界。

## 8. 阅读教程与开发节奏

不建议“一节教程读完就开发一节”。原因是教程后续可能已经给出方案和代码，过早自行补齐会造成返工。

也不建议一开始完整深读全部章节后再开发。原因是细节太多，等真正实现时仍然需要回看原文和代码，前期会消耗大量上下文。

建议采用“三层阅读法”：

1. 先读取全项目目录和章节标题，建立全局地图。
2. 对架构、环境、元数据、核心代码相关章节做预读，提取设计约束，但不急着写代码。
3. 到具体开发阶段，再精读对应章节和代码，并结合本项目差异化需求落地。

这种方式可以减少重复阅读，也能避免我在教程后续已有方案之前过早实现一套偏离太大的版本。

## 9. 资源与配置初步判断

教程第 3、4 章默认使用本地 Docker Compose 启动以下服务：

- MySQL：结构化元数据和模拟数仓。
- Qdrant：向量检索。
- Elasticsearch：字段值全文检索。
- Kibana：Elasticsearch 调试界面。
- Text Embedding Inference：Embedding 推理服务。
- FastAPI：后端 API 服务。

教程默认端口：

- MySQL：`3306`
- Elasticsearch：`9200`
- Kibana：`5601`
- Qdrant HTTP：`6333`
- Qdrant gRPC：`6334`
- Embedding：`8081`
- 后端 API：通常为 `8000`

本项目不按本地轻量化优先，建议资源规划按“云服务器长期运行 + 本地开发访问”设计：

- 数据库和检索服务优先部署在云服务器或托管云服务。
- 本地只保留开发代码、调试入口和必要的连接配置。
- 如果使用 Docker Compose，也应作为服务器端基础服务编排方式，而不是只服务一次性本地演示。
- 元数据库、业务数据源、检索索引、运行日志应分别规划备份和权限。

初步需要项目负责人后续提供或确认：

- 云服务器 SSH 管理权限。
- 数据库管理员账号，用于初始化库、表、只读账号和同步账号。
- 抖音主题域真实数据所在数据库地址、库名、访问方式。
- 钉钉开放平台应用凭证、AI 表格标识和接口访问权限。
- 大模型 API Key、服务地址和模型选择。
- 是否允许对外开放 Kibana、Qdrant Dashboard、Embedding docs 等调试入口；默认建议仅内网或 SSH 隧道访问。

## 10. 配置管理方向

教程使用 YAML 直接保存服务地址、账号和密钥。这个方式适合教学，但真实项目应拆分为：

- 可提交配置模板：保存配置结构和非敏感默认值。
- 本地或服务器环境变量：保存真实密码、API Key、Token。
- 部署环境配置：保存不同环境的数据库、索引服务和模型服务地址。

建议后续实现：

- `config/app.yaml`：非敏感默认配置。
- `.env`：本地开发密钥，不提交。
- `.env.example`：密钥模板，可提交。
- 配置加载层：合并 YAML 和环境变量，并做类型校验。
- 启动时配置自检：缺少关键配置时直接报错，不让系统以半配置状态运行。

## 11. 元数据同步设计调整

教程的元数据构建入口是 `meta_config.yaml`，由配置文件声明要同步哪些表、字段、指标和字段值。

本项目的入口调整为钉钉 AI 表格：

```text
钉钉 AI 表格
-> 钉钉开放平台接口
-> 同步任务拉取数据
-> 字段校验与标准化
-> 业务实体
-> 元数据数据库事务入库
-> 检索索引构建或更新
```

可以复用教程的分层思想：

- `scripts` 或定时任务入口只负责启动同步。
- `services` 负责读取钉钉数据、校验、标准化、事务编排。
- `repositories` 负责写元数据库、向量库、全文索引。
- `mappers` 负责业务实体和 ORM 模型转换。

需要调整的点：

- `meta_config.yaml` 不作为业务元数据主来源，只保留为本地测试或兜底模板。
- 钉钉表格中的表元数据、字段元数据要先映射为项目内部统一实体。
- 字段唯一 ID 建议使用 `库名.表名.字段名`，比教程的 `表名.字段名` 更适合真实多库场景。
- 字段类型、示例值、枚举值可以来自钉钉、真实数仓扫描或两者合并，入库前必须标记来源。
- 表元数据和字段元数据同批同步时需要事务保证一致性。
- 索引更新要考虑增量变更，避免每次全量重建影响线上查询。

## 12. 指标与字段的统一建模

教程将字段和指标拆成 `column_info`、`metric_info`、`column_metric`。

本项目产品概念上不强制区分指标和字段，因此建议运行时采用统一字段元数据模型，并通过字段属性表达差异：

- 原子字段：真实表中的物理字段。
- 计算字段：通过计算公式得到的字段。
- 业务度量字段：具有业务口径、聚合方式和使用注意事项的度量。
- 技术字段：分区、更新时间、删除标记等辅助字段。

为了保留扩展能力，数据库层可以增加依赖关系表：

- `meta_field_dependency`：记录字段直接依赖和血缘。
- `meta_field_formula` 或 `meta_field.calculation_formula`：记录计算公式。
- `meta_field.semantic_type`：记录标识字段、属性字段、度量字段、时间字段、技术字段。

这样既符合“不区分指标和字段”的产品治理方式，也能支持后续 SQL 生成时识别聚合字段、计算口径和依赖字段。

## 13. 在线问数上下文结构

教程最终交给模型的上下文主要包括：

- `table_infos`
- `metric_infos`
- `date_info`
- `db_info`
- `query`

本项目建议调整为：

- `question`：用户原始问题。
- `domain_context`：命中的主题域和业务对象。
- `table_context`：按库、表组织的表元数据。
- `field_context`：字段名、中文名、描述、类型、字段类型、业务含义、注意事项、示例值。
- `formula_context`：计算公式、聚合方式、依赖字段。
- `lineage_context`：直接依赖、字段血缘、可 join 关系。
- `value_context`：字段真实取值候选。
- `time_context`：当前日期、用户问题中的时间范围解析结果。
- `db_context`：数据库类型、版本、SQL 方言、执行账号权限。
- `safety_context`：允许访问的库表、禁止字段、最大执行时间、是否需要人工确认。

上下文序列化格式建议优先使用 YAML，因为层次结构对模型更易读；但系统内部仍应保存结构化 JSON，便于审计和调试。

## 14. SQL 生成与校验策略

教程使用生成 SQL、`EXPLAIN` 校验、失败后校正、再执行的闭环。

本项目需要在这个基础上增加更强的安全层：

- 只允许单条 `SELECT` 或受控只读查询。
- 禁止 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`TRUNCATE` 等写操作。
- 禁止多语句。
- 禁止访问未授权库表。
- 禁止返回敏感字段。
- 查询大表时优先要求时间范围、分区条件或其他限制条件。
- 校验通过不代表业务正确，结果为空要作为可诊断状态记录。
- 模型输出必须清理 Markdown 代码块和解释文字，只保留 SQL。
- SQL 修正应有最大次数限制，超过后返回可解释错误。

SQL 校验建议分三层：

1. 静态安全审查：解析 SQL AST 或保守规则检查。
2. 语法/执行计划校验：使用数据库 `EXPLAIN` 或等价机制。
3. 业务风险审查：检查大表扫描、缺少分区、字段敏感性、跨主题域访问等。

## 15. API 与前端协议

教程使用 FastAPI 暴露查询接口，并通过 SSE 返回流式进度。

本项目建议保留 SSE 方案：

- 用户提交一次问题。
- 后端持续推送节点进度、SQL、校验状态、执行结果或错误。
- 前端不需要双向长连接，SSE 比 WebSocket 更简单。

建议消息类型：

- `progress`：节点进度，包括节点名、状态、耗时、摘要。
- `sql`：生成的 SQL、校验状态、安全审查结果。
- `result`：最终查询结果、字段列表、行数、图表建议。
- `error`：全局错误或不可恢复错误。
- `trace`：可选调试信息，默认仅管理员或开发模式可见。

每条消息建议包含：

- `request_id`
- `type`
- `step`
- `status`
- `timestamp`
- `payload`

## 16. 依赖与生命周期管理

FastAPI 层建议分为：

- `main.py`：创建应用、注册生命周期和路由。
- `routers`：HTTP 请求和响应协议。
- `schemas`：请求体和响应结构。
- `dependencies`：组装 QueryService、Repository、Session、Client。
- `services`：业务编排。
- `lifespan`：启动时初始化外部客户端，关闭时释放资源。

资源生命周期建议：

- 数据库连接池、Qdrant/ES/OpenSearch 客户端、Embedding 客户端、大模型客户端：应用级资源。
- MySQL session、请求日志上下文、查询事务上下文：请求级资源。
- 用户问题、召回结果、SQL、结果集：任务级 State。

路由层只处理 HTTP 协议，不承载问数业务逻辑。一次查询应由 `QueryService` 转换成工作流执行，并统一包装成 SSE 输出。

## 17. 可观测性与日志追踪

真实服务必须支持并发请求追踪。建议从第一阶段就引入：

- `request_id`：每个请求唯一标识。
- `run_id`：每次问数任务唯一标识，可与 `request_id` 一致或独立。
- `step_id`：每个工作流节点唯一标识。
- 节点状态：`pending`、`running`、`success`、`error`、`blocked`。
- 节点耗时：开始时间、结束时间、耗时毫秒。
- 关键产物：召回上下文摘要、生成 SQL、校验结果、执行行数、错误信息。

错误处理原则：

- 节点失败后应停止后续依赖节点。
- 流式响应开始后，异常也要通过 SSE `error` 消息返回。
- SQL 校验失败属于可修正错误，系统可进入校正节点。
- 安全审查失败属于阻断错误，不应进入执行节点。

日志中不得输出真实密钥、数据库密码、钉钉 token、大模型 API Key。
