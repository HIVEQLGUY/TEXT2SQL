# 教程阅读路线

## 1. 阅读策略

本项目采用三层阅读法：

1. 先读取教程目录和章节标题，建立全局地图。
2. 对架构、环境、元数据、核心智能体流程相关章节做预读，只提取设计约束。
3. 到具体开发模块时，再精读对应章节和代码，并结合本项目的抖音主题域、钉钉 AI 表格元数据方案落地。

该策略用于避免两个问题：

- 逐章开发导致过早实现，后续教程已有方案时产生返工。
- 一次性深读全部内容导致上下文消耗过大，真正开发时仍需重复阅读。

## 3. 已读章节沉淀

### 1-项目概述与数仓基础

已沉淀内容：

- 智能问数属于 NL2SQL 项目。
- 用户自然语言问题需要转成可执行 SQL。
- 问数系统不是普通聊天助手，必须查询真实数据并返回结果。
- 业务数据库和数据仓库职责不同。
- 维度建模思想可参考，但教程电商表不是本项目实际表模型。

### 2-项目整体架构与智能体流程

已沉淀内容：

- 系统分为元数据构建期和在线问数查询期。
- 元数据知识库是 SQL 生成稳定性的核心基础。
- 教程方案使用 MySQL、Qdrant、Elasticsearch、Embedding 服务和 LangGraph。
- 问数链路包括关键词抽取、多路召回、合并、过滤、补充上下文、生成 SQL、校验 SQL、校正 SQL、执行 SQL。
- 本项目应吸收流程思想，但元数据来源改为钉钉 AI 表格，业务范围改为抖音主题域。

### 3-开发环境与基础服务准备

已沉淀内容：

- 教程后端使用 Python 3.12+。
- 教程推荐使用 `uv` 管理 Python 虚拟环境、依赖和锁文件。
- 教程后端依赖包括 FastAPI、SQLAlchemy、asyncmy、Qdrant client、Elasticsearch async client、LangChain、LangGraph、jieba、OmegaConf、PyYAML、Loguru 等。
- 教程基础服务包括 MySQL、Qdrant、Elasticsearch、Kibana、Text Embedding Inference。
- 教程建议用 Docker Compose 统一启动基础服务。
- 教程 Compose 默认端口包括 MySQL `3306`、Elasticsearch `9200`、Kibana `5601`、Qdrant `6333/6334`、Embedding `8081`。
- 教程 MySQL 同时承担元数据库和模拟数仓，真实项目中这两类库建议逻辑隔离，必要时物理隔离。

### 4-项目结构与基础服务配置管理

已沉淀内容：

- 教程后端项目采用分层目录：`agent`、`api`、`clients`、`conf`、`core`、`entities`、`models`、`prompt`、`repositories`、`scripts`、`services`。
- 教程将源码、配置、提示词、脚本分离管理。
- 教程使用 YAML 管理 MySQL、Qdrant、Embedding、Elasticsearch、LLM 和日志配置。
- 教程使用 `dataclass + OmegaConf` 将 YAML 加载为结构化配置对象。
- 本项目可以沿用“集中配置 + 类型化配置对象”的思想，但真实密钥应通过环境变量或密钥管理注入，不应直接写入 YAML。

### 7-元数据知识库总览与构建入口

已沉淀内容：

- 元数据知识库是问数智能体稳定生成 SQL 的前提。
- 教程同步脚本不是单纯入库，而是调度完整知识构建流程。
- 教程采用 `scripts -> services -> repositories -> mappers/models` 的分层。
- 教程区分配置文件、业务实体、ORM 模型和 Mapper。
- 教程的构建流程包括读取配置、写元数据库、写 Qdrant 字段向量、写 ES 字段值、写指标信息和指标向量。
- 本项目应复用“入口轻、服务层编排、仓储层读写、事务集中管理”的工程思想。

### 8-表与字段信息同步到元数据库

已沉淀内容：

- 教程通过 `_save_tables_to_meta_db(...)` 将配置里的表和字段转成业务实体，再写入元数据库。
- 字段唯一 ID 使用 `表名.字段名`，避免不同表同名字段冲突。
- 字段类型和字段示例值不直接来自配置，而是运行时从数仓查询补齐。
- 字段类型适合按表查询，字段示例值适合按字段查询。
- Service 层先处理业务实体，Repository 层负责落库，Mapper 负责业务实体和 ORM 模型转换。
- 表信息和字段信息属于同一批业务操作，应放在同一个事务边界里，要么一起成功，要么一起失败。
- 本项目中，教程的 `meta_config.yaml` 会被钉钉 AI 表格同步数据替代，但“同步标准化后再入元数据库”的主线仍然适用。

### 9-字段与指标检索能力构建

已沉淀内容：

- 字段检索不能只靠一种能力：向量索引解决字段语义召回，全文索引解决真实字段值匹配。
- 一个字段不应只生成一个向量 point，应按字段名、字段描述、字段别名等拆成多个语义入口。
- Qdrant payload 可以直接保存完整字段上下文，换取查询链路更简单。
- 不是所有字段都需要同步真实值，适合全文索引的是可能被用户作为过滤条件表达的维度字段。
- 字段值索引用于确认库里到底存的是“河北”还是“河北省”这类真实值。
- 教程将指标作为独立知识对象，并为指标建立独立向量 collection。
- 本项目产品概念上不强制区分指标和字段，但应支持“带计算公式、业务口径、依赖关系的计算字段/业务字段”进入同一套检索体系。

### 10-问数智能体总览与工作流骨架

已沉淀内容：

- 教程使用 LangGraph 表达可执行工作流，而不是简单 `Prompt -> Model -> SQL`。
- LangGraph 适合本项目的原因是：多步骤、共享状态、并行分支、条件分支、流式进度输出。
- `State` 保存业务中间结果，不能当作随手塞变量的字典，应有明确 schema。
- `Runtime Context` 保存运行时依赖，例如 LLM、Repository、客户端等，和状态数据分离。
- 教程使用 `custom` streaming，让节点主动输出执行进度，适合前端展示流程状态。

### 11-关键词抽取与多路召回

已沉淀内容：

- 三路召回分别解决：字段解决“查哪一列”，指标解决“怎么算”，字段取值解决“条件值怎么写”。
- 字段召回需要关键词扩展，以提高自然语言到字段元数据的召回率。
- 指标召回用于把 GMV、销售总额、成交额等表达映射到业务口径。
- 字段取值召回用于确认数据库真实值，例如“河北”还是“河北省”。
- 召回结果要按字段 ID 去重，因为一个字段可能通过名称、描述、别名等多个 point 被重复召回。
- 本项目应将三路召回调整为：字段元数据召回、计算字段/业务口径召回、字段值召回、依赖/血缘召回。

### 12-召回信息合并与上下文构建

已沉淀内容：

- 召回结果不能直接交给大模型，因为它们是分散的字段、指标和值。
- 合并节点不调用大模型，主要做结构化整理和必要的元数据库反查。
- 指标依赖字段必须补进字段列表，否则只知道指标名无法生成 SQL。
- 字段取值要补进对应字段的 examples 或候选值里。
- 每张表需要补充主键和外键，避免 join 所需字段在召回阶段丢失。
- 合并目标是生成按表组织的上下文，而不是散乱字段列表。

### 13-SQL生成前的信息过滤与补全

已沉淀内容：

- 合并后的上下文仍可能过宽，需要在 SQL 生成前过滤。
- 表过滤会同时过滤字段，保留当前问题真正需要的表和字段。
- 指标过滤允许返回空数组，不是每个问题都必须命中业务指标。
- 上下文需要转成文本给大模型，教程选择 YAML，因为层次结构更易读。
- 额外上下文不是业务元数据，包括当前日期、数据库类型、数据库版本等运行环境信息。

### 14-SQL生成与执行闭环

已沉淀内容：

- SQL 生成前已具备用户问题、表字段上下文、指标口径、日期信息、数据库方言和版本。
- SQL 生成提示词核心输入包括 `table_infos`、`metric_infos`、`date_info`、`db_info`、`query`。
- SQL 生成后先校验，不直接执行。
- 校验失败时通过条件分支进入 SQL 校正节点，校正时应携带原上下文和数据库错误信息。
- 常见问题包括模型输出 Markdown 代码块、Unknown column、校验通过但结果为空、校正后仍失败。
- 本项目需要在教程 `EXPLAIN` 校验基础上增加 SQL 安全审查和权限控制。

### 15-API接口基础与FastAPI入门

已沉淀内容：

- 查询接口用于把前端自然语言问题接入后端问数流程。
- 问数链路耗时可能较长，普通一次性 HTTP 响应不适合展示中间过程。
- 教程选择 SSE 流式响应，因为前端只需提交一次问题，后端持续推送进度和结果。
- SSE 比 WebSocket 更轻量，适合任务进度、日志流和模型输出流。
- FastAPI 的 `lifespan` 适合初始化应用级外部资源，例如 Embedding、Qdrant、ES、MySQL 客户端。
- FastAPI 的 `Depends` 用于声明接口需要的对象，由框架负责组装依赖。

### 16-查询接口实现与依赖组装

已沉淀内容：

- 路由层只处理 HTTP 相关逻辑，不应堆业务流程。
- `QueryService` 将一次 HTTP 请求转换成一次工作流执行。
- `QueryService` 负责创建 State、Context，调用图工作流，并把输出包装成 SSE。
- State 保存本次任务不断变化的业务数据；Context 保存 Repository、Client、LLM 等运行时依赖。
- 流式响应一旦开始写出，异常也应包装成 SSE 消息返回给前端。
- MySQL Session 是请求级资源，应通过带 `yield` 的依赖项管理。
- 外部客户端适合在 FastAPI `lifespan` 中初始化和关闭。

### 17-前后端联调与日志追踪

已沉淀内容：

- 前后端需要统一 SSE 消息协议。
- 教程约定三类消息：`progress`、`result`、`error`。
- `progress` 表示节点执行进度，`result` 表示最终查询结果，`error` 表示全局错误。
- 节点失败后必须停止错误链路，避免上下文不完整时继续生成或执行 SQL。
- 并发请求需要 `request_id` 追踪日志。
- 中间件生成 `request_id`，ContextVar 保存请求上下文，Loguru 自动带上 `request_id`。

## 4. 下一步预读顺序

建议预读顺序：

第二层预读已覆盖教程主线。后续进入开发时，按模块精读对应章节和代码。

`5` 和 `6` 涉及具体基础服务，可在确定服务器、数据库、索引组件选型时再精读。

## 5. 本项目差异化约束

- 第一阶段使用抖音主题域真实数据，不使用教程电商教学表作为落地模型。
- 元数据协作入口是钉钉 AI 表格。
- 元数据通过钉钉开放平台接口定时同步到项目元数据数据库。
- 产品概念上不强制区分指标和字段。
- 字段元数据需要支持计算公式、直接依赖、业务含义和使用注意事项。
- 表元数据需要支持主题域、数仓层级、表粒度、更新频率、负责人、适用/不适用场景等治理字段。
- 资源不按本地轻量化优先，可以使用云服务器和数据库管理员权限搭建长期架构。
