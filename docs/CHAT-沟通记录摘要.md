# 沟通记录摘要

## 1. 项目目标

项目目标是搭建一个系统性的智能问数项目。用户会逐步提供教程和业务文档，Codex 负责理解文档、分析搭建思路、判断环境与资源需求，并从系统工程角度给出实现建议和代码落地。

用户代码经验较弱，因此 Codex 需要主动识别工程规范、配置风险、系统健壮性问题，而不是只按教程机械实现。

## 2. 教程阅读策略

已确认采用“三层阅读法”：

1. 先读取教程目录和章节标题，建立全局地图。
2. 对架构、环境、元数据、核心智能体流程相关章节做预读，只提取设计约束。
3. 到具体开发模块时，再精读对应章节和代码，并结合本项目差异化需求落地。

采用该策略的原因：

- 避免一节一开发导致过早实现，后续教程已有方案时产生返工。
- 避免一次性深读全部内容导致上下文消耗过大，真正开发时仍需重复阅读。

## 4. 关键业务差异

本项目不是照教程做电商 demo，而是做真实业务智能问数系统。

第一阶段业务范围：

- 优先跑通抖音主题域的数据和元数据。
- 不使用教程中的 `fact_order`、`dim_product`、`dim_customer` 等教学表作为实际模型。

元数据入口：

- 未来元数据主要通过钉钉 AI 表格协作维护。
- 借助钉钉 AI 字段能力自动生成元数据描述。
- 人工补充指标计算口径、字段血缘、直接依赖和使用注意事项。
- 系统通过钉钉开放平台接口定时同步元数据到项目元数据库。

指标和字段关系：

- 产品概念上不强制区分指标和字段。
- 指标可以作为带计算公式、业务口径和依赖关系的特殊字段元数据来管理。

## 6. 架构方向

已确认第一阶段架构方向：

- 后端：FastAPI
- 流式协议：SSE
- 工作流：保留 LangGraph 或至少保持同等节点化结构
- 元数据入口：钉钉 AI 表格
- 运行元数据：项目自己的元数据库
- 检索：字段语义检索 + 字段值检索 + 字段依赖/计算公式上下文
- SQL：生成后必须经过安全审查、语法校验、风险校验，再执行
- 日志：从第一阶段引入 `request_id`、`run_id`、`step_id`

资源原则：

- 不为了省本地资源做临时架构。
- 可以使用云服务器和数据库管理员权限搭建长期架构。
- 但应用运行仍应遵守最小权限原则，问数执行默认使用只读账号。
